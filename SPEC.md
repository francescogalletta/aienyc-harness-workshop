# Harness contract

This file is the contract every build step follows. The build prompts in
`prompts/` tell a coding agent *what to build next*; this file says *what it
must look like*, so that two people running the same prompt end up with
harnesses that fit together.

If a prompt and this file disagree, this file wins. Do not edit this file,
the tests, or the example data while running a build prompt.

Status of each section:

| Section | Status |
| --- | --- |
| 1. Ground rules | Fixed |
| 2. Layout | Fixed |
| 3. Step 0: setup | Fixed, covered by `tests/step0` |
| 4. Steps 1 to 5 | Draft. Each is fixed when its step is built and its tests are written. |

## 1. Ground rules

These hold for every step.

1. **A number reaches the person only from tested code, through the local
   database, never from the model's own text.**
2. **The harness is not about weddings.** Nothing under `harness/` may name
   the example domain, its files, or its column names. The example lives in
   `data/example/` and, from step 1, in the domain brief.
3. **The harness is not tied to a model provider.** Only files under
   `harness/model/` may import a provider SDK. Everything else talks to the
   `Model` interface in section 3.2.
4. **The harness is not tied to an input format.** Raw files are read through
   source adapters that map them to a canonical shape (section 4, step 2).
   No calculation reads a raw file.
5. **Everything that matters is written to the database.** Nothing the person
   may need to inspect lives only in memory or only in the chat.
6. **The model that reads web pages never holds the person's financial data.**
   Online research runs in a session with no access to the data tools.
7. Python 3.11 or later. Standard library first. A dependency is added only
   where this file names it.

## 2. Layout

```
SPEC.md            this contract
BUILD_PLAN.md      the steps, and how each one is proven
prompts/           one build prompt per step
harness/           the harness (built by the prompts)
  model/           the only place a provider SDK may be imported
  migrations/      numbered .sql files, applied in order
tests/stepN/       acceptance tests for step N (given, never edited)
tests/data/        tests for the example data (given)
data/generate.py   seeded generator for the example data (given)
data/example/      the generated example files (given)
var/               runtime files such as the database (not committed)
```

## 3. Step 0: setup

Step 0 builds the three things every later step stands on: a way to talk to a
model, a stand-in for the model so the harness can be tested offline, and the
local database.

### 3.1 Configuration: `harness/config.py`

Read from environment variables, each with a default:

| Variable | Default | Meaning |
| --- | --- | --- |
| `HARNESS_DB` | `var/harness.db` | Path of the SQLite database |
| `HARNESS_MODEL_PROVIDER` | `anthropic` | `anthropic` or `scripted` |
| `HARNESS_MODEL` | `claude-sonnet-5-5` | Model name passed to the provider |
| `HARNESS_SCRIPT` | (none) | Path of a script file for the `scripted` provider |

Expose `load_config() -> Config`, a frozen dataclass with the fields
`db_path: pathlib.Path`, `model_provider: str`, `model_name: str`,
`script_path: pathlib.Path | None`. It reads the environment on every call.

### 3.2 Model interface: `harness/model/`

The four types below live in `harness/model/interface.py`.
`harness/model/__init__.py` re-exports them and lists exactly these names in
`__all__`: `ToolSpec`, `ToolCall`, `ModelResponse`, `Model`, `ScriptedModel`,
`ScriptExhausted`, `get_model`. Other code imports from `harness.model`, never
from its submodules.

Importing `harness.model` must not import any provider SDK.

```python
@dataclass(frozen=True)
class ToolSpec:
    name: str
    description: str
    input_schema: dict          # JSON Schema for the arguments

@dataclass(frozen=True)
class ToolCall:
    id: str
    name: str
    arguments: dict

@dataclass(frozen=True)
class ModelResponse:
    text: str                           # "" if the model said nothing
    tool_calls: tuple[ToolCall, ...]    # () if it called no tools
    stop_reason: str                    # "end" | "tool_use" | "max_tokens" | "other"
    usage: dict                         # {"input_tokens": int, "output_tokens": int}

class Model(Protocol):
    def complete(self, *, system: str, messages: list[dict],
                 tools: Sequence[ToolSpec] = ()) -> ModelResponse: ...
```

Messages are plain dicts in one neutral format, whatever the provider:

```python
{"role": "user", "content": "text"}
{"role": "assistant", "content": "text", "tool_calls": [{"id": "...", "name": "...", "arguments": {...}}]}
{"role": "tool", "tool_call_id": "...", "content": "text", "is_error": True}
```

`tool_calls` may be missing or empty on an assistant message. `is_error` is
optional on a tool message and marks a tool call that failed.

`get_model(provider: str | None = None) -> Model` returns the model for the
given provider, or for `load_config().model_provider` when none is given.
An unknown provider raises `ValueError` naming the provider. For `anthropic`
it returns `AnthropicModel(load_config().model_name)`, importing that file
only at that moment.

### 3.3 Scripted stand-in: `harness/model/scripted.py`

`ScriptedModel(script: list[dict])` replays prepared responses in order.
Each script entry is a dict with optional keys `text` (default `""`),
`tool_calls` (default `[]`, each `{"name": ..., "arguments": {...}}` with an
optional `id`) and `stop_reason`.

- `complete(...)` returns the next entry as a `ModelResponse`. If the entry
  has no `stop_reason`, it is `"tool_use"` when there are tool calls and
  `"end"` otherwise. A tool call without an `id` gets `call_1`, `call_2`, ...
  numbered across the whole script. A tool call that brings its own `id`
  does not use up a number.
- `usage` is `{"input_tokens": 0, "output_tokens": 0}`.
- Every call is appended to `self.calls` as
  `{"system": ..., "messages": ..., "tools": ...}` so tests can see what the
  harness sent.
- When the script is used up, `complete` raises `ScriptExhausted`, a
  subclass of `Exception`.
- `ScriptedModel.from_file(path)` loads a JSON file holding the list.

`get_model("scripted")` loads the file named by `HARNESS_SCRIPT`. With no
script path set it returns a model with the one-entry script
`[{"text": "ok"}]`.

### 3.4 Claude adapter: `harness/model/anthropic_provider.py`

`AnthropicModel(model_name: str, client=None, max_tokens: int = 4096)`.
The `anthropic` package is imported inside this file only, and only when no
`client` is passed in. A passed-in `client` is used as is, which is how the
tests run it without a network.

`complete` calls `client.messages.create(model=..., max_tokens=...,
system=..., messages=..., tools=...)`. It omits `tools` when there are none
and `system` when it is the empty string. It translates in both directions:

| Neutral | Claude API |
| --- | --- |
| user message | `{"role": "user", "content": text}` |
| assistant message | `{"role": "assistant", "content": [text block if text is not empty, then one `tool_use` block per tool call with `id`, `name`, `input`]}` |
| tool message | a `tool_result` block `{"type": "tool_result", "tool_use_id": ..., "content": text}` inside a `user` message, with `"is_error": True` added when the tool message has it set. Consecutive tool messages go into **one** user message. |
| `ToolSpec` | `{"name", "description", "input_schema"}` |

An assistant message with no text and no tool calls is left out, because the
API rejects an empty message.

From the response: join the `text` blocks into `text` with nothing between
them; turn each `tool_use`
block into a `ToolCall`; map `stop_reason` `end_turn` to `"end"`, `tool_use`
to `"tool_use"`, `max_tokens` to `"max_tokens"`, anything else to `"other"`;
copy `input_tokens` and `output_tokens` from `usage`.

### 3.5 Database: `harness/db.py` and `harness/migrations/`

SQLite, through the standard `sqlite3` module.

- `connect(path=None) -> sqlite3.Connection` opens the database at `path`,
  or at `load_config().db_path`. It creates the parent folder, sets
  `row_factory = sqlite3.Row` and turns foreign keys on.
- `migrate(conn) -> list[str]` applies every `harness/migrations/*.sql` file
  not yet applied, in filename order, and returns the file names it applied
  this time (for example `["0001_init.sql"]`). Applied names are kept in a
  table `schema_migrations(name, applied_at)`. Running it twice applies
  nothing the second time. `migrate` creates `schema_migrations` itself.
- `applied_migrations(conn) -> list[str]` returns every applied file name,
  in order, whenever it was applied.
- `record_event(conn, *, session_id: str, kind: str, actor: str, payload: dict) -> int`
  inserts one row and returns its id. `ts` is
  `datetime.now(timezone.utc).isoformat()`, so it carries the `+00:00` offset.
- `list_events(conn, *, session_id=None, kind=None) -> list[sqlite3.Row]`
  returns matching rows, oldest first (ordered by `id`).

`migrate` and `record_event` commit before they return, so another process
opening the same file sees the result.

A **session id** is any string that groups the events of one run. Code that
starts a run makes one with `uuid.uuid4().hex`.

`0001_init.sql` creates one table:

```sql
CREATE TABLE events (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    ts          TEXT NOT NULL,      -- UTC, ISO 8601
    session_id  TEXT NOT NULL,
    kind        TEXT NOT NULL,      -- dotted name, e.g. "harness.check"
    actor       TEXT NOT NULL,      -- "harness" | "agent" | "person"
    payload     TEXT NOT NULL       -- JSON object
);
```

`events` is append-only. The migration adds triggers so that any `UPDATE` or
`DELETE` on it fails with the message `events is append-only`. A record that
can be edited afterwards is not evidence.

`actor` must be one of the three values; anything else raises `ValueError`
before the insert.

### 3.6 Command line: `harness/__main__.py`

`python -m harness check` proves the setup end to end. It:

1. opens the database and runs `migrate`;
2. gets the configured model and sends one user message, `ping`;
3. records one event of kind `harness.check`, actor `harness`, with a new
   session id, whose payload holds `provider`, `model` (the configured model
   name), `reply` (the response text) and `migrations` (the result of
   `applied_migrations`);
4. prints the provider, the model name, the database path as configured,
   and the reply, to standard output;
5. exits 0. If getting the model or calling it fails, it prints one line
   describing the error to standard error, with no traceback, exits 1, and
   records nothing.

With the `scripted` provider no real model is called. The recorded `provider`
says so; `model` is still the configured name.

`python -m harness events` runs `migrate`, then prints the events table,
oldest first, one line each: id, ts, kind, actor, separated by spaces.

Run every command from the repository root. The default database path is
relative to the current folder.

## 4. Steps 1 to 5 (draft)

Each step adds modules and tables without changing what earlier steps built.
New tables arrive as new migration files. The detail below is the intended
shape; it becomes fixed when the step is built.

**Step 1, shared domain.** `harness/grounding/`: an interview loop that asks
one question at a time, a `Researcher` interface for looking up standard
definitions (one implementation using the provider's web search, one reading
a saved reference file for offline runs), and a writer for the domain brief.
The brief is saved as `brief/domain_brief.md` plus a machine-readable
`brief/domain_brief.json` with: `goal`, `scope`, `glossary`, `particulars`
(each with a handling rule), `process` (steps tagged `calculation`,
`judgment` or `input`, and what feeds what) and `definition_of_done`.

**Step 2, consistency.** `harness/sources/`: adapters that map a raw file to
canonical records, checked against a schema. `harness/calc/`: a registry of
calculation modules, each a pure function with typed inputs and outputs,
unit tests and golden examples. `harness/gate.py`: runs a module's tests and
refuses to call it if they fail. `harness/select.py`: turns a request into a
proposed call (module, inputs, assumptions, expected result). New tables:
`modules`, `test_runs`, `proposed_calls`, `calc_runs`. Dependencies allowed
from here: `pandas`, `pandera`, `numpy-financial`.

**Step 3, evidence.** Every model call, tool call and agent choice is
recorded as an event. `harness/evidence/`: a small local web page with three
views read straight from the database: the process end to end, one
calculation step by step, and module test status. No model call is involved
in rendering any of it.

**Step 4, human in the loop.** `harness/side/`: a sub-agent with its own
context that holds a clarification with the person and returns only a
decision record. Gates sit before a calculation runs, on the proposed inputs
and the expected output. New table: `decisions`.

**Step 5, verification.** `harness/verify.py`: at the decision points named
in the brief, checks new information against the person's own data, the
brief, or a reference source. A mismatch opens a side conversation.
New table: `verifications`.
